## 0) Toolchain & Workflow Guide

### Tool Map (what each tool is best for in **this** project)

* **GPT‑5.2 Pro**

  * Spec extraction → turn Appendix LOCKED text into *compact, enforceable* engineering checklists.
  * Ledger audits (field-by-field + payload-by-payload) against Appendix §2.1–§2.3.

* **Gemini 3 Pro**

* **Grok 4 / Grok 4.1 Thinking Beta**

  * Performance profiling interpretation: why frames drop, where layout thrash happens.
* **Cursor**

  * Primary implementation engine (web + API + SQL migrations + tests).
  * Best for multi-file refactors while keeping `project_rules.md` + `.cursorrules` pinned.
* **v0.dev**

  * Rapid scaffolding of *non-physics* UI shells (modals, pill UI, forms), then hand-edit to comply with LOCKED interactions and Ledger rules.

### Workflow Patterns (2–3 end-to-end loops)

1. **LOCKED slice → Implement → Gate**

   * Extract 1 Appendix slice (e.g., §3.1 + §3.9).
   * Implement minimal feature.
   * Run *the gate that matches the slice* (pointer safety test, tactile script, etc.).
   * Only then move on. (Avoid multi-slice coding sessions.)

2. **Tactile Micro‑Tune Loop**

   * Make one small change to physics/animation constants (or one algorithm).
   * Run the “vibe script” on iOS Safari + Android Chrome + desktop.
   * If better: bump `PHYSICS_SPEC_VERSION` and commit. If not: revert. 

3. **Ledger Gate Loop**

   * Every time you add a DB column / API field / cache / log line:

     * classify it (plaintext allowed vs ciphertext required) using §2.3 and §2.1–§2.2. 
     * run packet-sniff verification for flows that touch network (upload, auth). 

### Failure Loop Protocol (CRITICAL)

**When a Quality Gate fails:**

1. **Diagnose Checklist**

   * Did we violate a LOCKED rule (scroll physics, >2 generations, state names)? 
   * Did we break Ledger (plaintext meaning/PII in server/payload/log)? 
   * Did we introduce a perf regression (layout thrash, main-thread crypto, React re-render storms)?

2. **Smallest Fix First**

   * Patch the minimal function / constant.
   * Avoid refactors until the gate passes.

3. **Retest Quickly**

   * Re-run only the failing gate (unit test / Playwright / manual script).
   * If it passes, then run the “adjacent” gate (e.g., after pointer fix, run FSM drag script).

4. **When to Rollback**

   * If **tactile gate fails twice in a row** after attempted minimal fixes: revert to last passing commit and escalate (see routing).
   * If **ledger gate fails once**: **STOP THE LINE** until fixed (no further features). 

5. **Escalation Routing**

   * **Physics/tactile**: escalate to Grok 4.1 Thinking Beta with minimal repro + video + constants file.
   * **Build/test**: escalate to Gemini for CI / TS / bundler diagnosis.
   * **Ledger/security**: escalate to GPT‑5.2 Pro for field-by-field redesign + packet-sniff plan.
   * **Schema drift**: escalate to GPT‑5.2 Pro + DB migration owner; enforce Appendix §7.1 names.

- Paternal branch curves up/out RIGHT, lands on INNER SIDE of RIGHT parent bubble.
- Line must land on SIDE of each parent bubble (not top/bottom).

- Anchors must update during FSM travel sequences and lens toggles.

- When nodes hide/collapse, they must visually "suck into" or "fold behind" the Focus bubble.
- No simple dissolve/cross-fade shortcut.

## 8) Lens Toggle Fidelity (Architect Override E)
- Lens switching must be Unplug/Replug:
  retract old line → fade old node → fade new node → extend new line.
- No simple cross-fade between states.

## 9) Viewport Stability (Architect Override F)
- Main tactile surface must not jitter/resize due to mobile browser UI.
- Do not rely on naive 100vh if it causes address-bar jitter.
- Must pass iOS Safari + Android Chrome stability gate.

## 1) Strategy

### Cost-Effectiveness Strategy (minimize token waste + rework while staying compliant)

* **Front-load contracts that cause rework if wrong**:

  * Pointer/rail architecture (because it touches every frame). 
  * Geometry/anchors and “only-lines-for-core-nodes” (because it shapes the renderer). 
  * Schema/enums naming contract (because drift is expensive to unwind). 
  * Ledger mapping + logging rules (because one violation forces redesign). 
* **Use fixtures until UI physics is stable**:

  * Don’t block tactile iteration on API/DB; instead use a `VaultRepo` interface with a fixture implementation (details below).
* **Gates over “big bang”**:

  * Each LOCKED slice gets a corresponding gate (tests + device checks). If a gate fails, fix before moving on. 

### Data Strategy (CRITICAL): feed Tactile Core UI early **without** blocking on DB/API

**Goal:** Build the thick-client renderer + FSM using realistic shapes **before** backend exists, without later rewrites.

**Approach:** Define a stable client contract:

* `VaultRepo` interface returns **UI-ready decrypted shapes** (names/DOB/etc) *in memory only*.
* `FixtureVaultRepo` supplies deterministic demo data (plaintext in repo fixtures, never transmitted).
* Later, `ApiVaultRepo` fetches ciphertext blobs + envelopes, decrypts client-side, returns the same UI shapes. This aligns with Thick Client doctrine. 

**Key design invariant:** The UI layer never talks to “encrypted blobs” directly. The repo layer is the seam.

**Transition to real schema later**

* Fixture IDs match UUID format and table semantics (profiles/relationships/memories).
* The `ApiVaultRepo` will map from Appendix §7.1 rows into the same UI shapes.

## 2) Master Build Sequence (CORE OUTPUT)

### Ordering Justifications (MANDATORY)

**(a) Dumb Rail vs Smart Brain (FSM layering)**
We implement the **dumb rail** (pointer capture, 1:1 deltas, stable viewport, perf-safe rendering) *before* full FSM choreography, because §3.1 and §3.9 are non-negotiable foundations: any FSM work built on unstable pointer/viewport will be rework.  

**(b) Schema-lock timing vs other work**
We lock the Postgres schema contract early because column/enums are binding and drift is expensive to unwind (§7.1). 
But we *do not* block UI: the UI consumes fixture-backed `VaultRepo` first.

**(c) Crypto timing vs API/UI work**
We delay full crypto until after tactile core is stable (to avoid two moving targets), but we implement crypto **before any networked upload/auth flows** so we don’t violate “encrypt before leaving device” and the packet-sniff gate (§0.1, §1.3, §12).

### Step S06 — Curved “Bezier Y” Geometry + Anchors (Overrides A+B) + Connector Truth Table (LOCKED §3.4)

**Definition of Success (verifiable):**

**Dependencies:** S05.

* Secondary: Grok 4.1 (visual tuning)
* Mode: Implementation + Test
* Why: geometry is precise; needs tests + tuning.

#### Binding Geometry Spec (implementable, no guesswork)

**Coordinate space**

* Use **surface-local coordinates** in CSS pixels:

  * origin (0,0) at surface top-left
  * x increases right; y increases down
* Nodes store center positions `{cx, cy}` in this space.
* Bubble sizes are constants (or derived from scale), so anchors are computed mathematically (no `getBoundingClientRect` during drag).

**Anchor points (explicit)**

* Focus bubble:

  * `focusStemAnchor = (focus.cx, focus.cy - focus.radius)` (top-center boundary)
* Generation Label bubble:

  * `labelBranchAnchor = (label.cx, label.cy - label.radius)` (**top-center** boundary) — **Override A origin**
  * `labelStemAnchor   = (label.cx, label.cy + label.radius)` (bottom-center boundary)
* Left parent bubble:

  * `leftParentInnerAnchor = (left.cx + left.radius, left.cy)` (right-middle boundary)
* Right parent bubble:

  * `rightParentInnerAnchor = (right.cx - right.radius, right.cy)` (left-middle boundary)

**Bezier control point strategy**

* For each branch (cubic bezier):

  * start `S = labelBranchAnchor`
  * end `E = parentInnerAnchor`
  * `dx = E.x - S.x`, `dy = E.y - S.y` (dy is negative in REST)
  * control point 1 (vertical “vein rise”):

    * `C1 = (S.x, S.y + dy * 0.55)`  (moves upward because dy < 0)
  * control point 2 (horizontal “side entry” tangent):

    * `C2 = (E.x - dx * 0.45, E.y)` (forces horizontal tangent at end)
  * Path: `M S.x S.y C C1.x C1.y, C2.x C2.y, E.x E.y`

* Stem (cubic bezier) from focus to label:

  * start `Sf = focusStemAnchor`
  * end `El = labelStemAnchor`
  * `dy = El.y - Sf.y` (dy is negative in REST because label above focus)
  * `C1 = (Sf.x, Sf.y + dy * 0.35)`
  * `C2 = (El.x, El.y - dy * 0.35)`
  * Path: `M Sf ... C ... El ...`

**Responsiveness rules**

* Bubble radii scale with viewport min dimension:

  * `radius = clamp(28, min(vw,vh)*0.06, 48)` (example; keep as constant in code with tests)
* Parent separation scales similarly.
* On resize (stable viewport update), recompute base node positions and therefore anchors.
* During drag/FSM:

  * node centers are updated by rail/FSM; anchors derived from centers; connectors recomputed every RAF tick.

**Updates during lens toggles**

* Lens toggle sequence (S07) will:

  * animate the branch path length from 100% → 0% (retract to labelBranchAnchor)
  * swap endpoint node data
  * animate 0% → 100% to new endpoint

**Updates during FSM travel sequences**

* As Focus/Label/Parents move, anchors update automatically from their centers.
* No DOM reads during movement.

  1. Identify which exact checklist bullet failed.
  2. Reproduce with minimal steps.
  3. Decide if it’s physics, ledger, auth, or transfer.
* Smallest fix: patch minimal surface area.
* Retest: re-run only the failed gate.
* Rollback: if physics gate fails twice, revert and escalate; if ledger fails once, stop the line.
* Pivot prompts:

  * Physics: “Diagnose why spring drift breaks 1:1 deltas; propose minimal patch.”
  * Ledger: “Here is packet-sniff output; identify any plaintext leakage and where it originates in code.”

## 3) Decision Checkpoints (Forks in the Road)

1. **Auth method consistent with “no password in network payload”**

* Option A: Passwordless auth (email OTP/magic link or passkey) + vault password only for ARK derivation client-side.
* Option B: Password auth via Better Auth (would likely transmit password).
* Recommendation: **A**, because Appendix explicitly states raw password never appears in network payloads. 
  Decision owner: Architect + Security.

2. **Key envelope crypto library**

* Option A: libsodium.js sealed box (preferred) 
* Option B: ECDH + HKDF + AES‑GCM fallback 
* Recommendation: Start with **A** if bundle size acceptable; keep B as fallback behind feature flag.
  Decision owner: Architect.

3. **Client decrypted data persistence**

* Option A: Decrypted data only in memory (ephemeral); re-derive/unlock each session.
* Option B: Persist decrypted cache locally (riskier).
* Recommendation: **A** aligns with sovereignty minimization and avoids local leakage (no spec for persistent decrypted cache). 
  Decision owner: Security + Product.

4. **Chunked encryption format for large files**

* Option A: Whole-file AES-GCM (simple, may OOM).
* Option B: Chunked AES-GCM per chunk + manifest (scales, more code).
* Recommendation: **B** for web-first longevity; still off-main-thread per Override G.
  Decision owner: Architect.

5. **Membership model (multi-family)**

* Option A: Single-family-per-account MVP derived from profile_claim.
* Option B: Multi-family membership (needs explicit model).
* Recommendation: Start with **A** (simpler) but design schema extension path; membership table is NOT SPECIFIED. 
  Decision owner: Product + Architect.

## 5) Open Questions / Missing Specs

Anything here is **NOT SPECIFIED IN DOCS** (and not closed by Architect Overrides). Each item includes a Sovereign-aligned recommendation.

### 5.1 Membership model: “account ↔ family association(s)”

* Status: **NOT SPECIFIED IN DOCS** (concept exists, but no table/endpoint contract). 
* Recommendation (Sovereign-aligned): Start MVP with **single family per account** derived from `profile_claims.profile_id → profiles.family_id`. Add explicit membership table later if multi-family becomes required.
* Risks if chosen differently:

  * If multi-family is needed soon, retrofitting authorization gates later is nontrivial.
* Decision owner: Product + Architect.

### 5.2 Auth/login flow details under Better Auth

* Status: **NOT SPECIFIED IN DOCS** (only requirements for device inventory/revocation). 
* Recommendation: Use passkeys or email OTP for authentication, and use password only as vault secret (to satisfy “no password in network payload”). 
* Risks: More onboarding friction; passkey UX varies by device.
* Decision owner: Architect + Security + Product.

### 5.3 Profile blob and memory metadata blob internal schemas

* Status: **NOT SPECIFIED IN DOCS** (only says blobs exist and are encrypted). 
* Recommendation: Versioned JSON (CBOR optional) inside blobs:

  * include `schema_version`, `display_name`, `dob`, `dob_precision`, etc for profile
  * include `title`, `description`, `event_date`, `approx_precision`, `oral_history_flag`, `people_tags` for memory
* Risks: Poor schema design can lock you into migrations; mitigate with versioning fields already supported (`profile_blob_version`, `metadata_blob_version`).  
* Decision owner: Architect.

### 5.4 Custodian Death / Loss / Recovery protocols (mandatory gap detection)

* Status: **NOT SPECIFIED IN DOCS**
* Recommendation: Add a “Recovery” design that does not violate zero-knowledge:

  * Require child (when eligible) to be ultimate recovery authority.
  * Before eligible_at, allow *multiple custodians* (2-of-3 style) via custody_bridge envelopes, but this implies additional spec.
* Risks: Any recovery mechanism risks reintroducing server-held master keys (forbidden). 
* Decision owner: Security + Legal + Architect.

### 5.5 Shared write authority / conflict resolution (multi-user edits) (mandatory gap detection)

* Status: **NOT SPECIFIED IN DOCS**
* Recommendation: Adopt server-side “last write wins” for ciphertext blobs with optimistic concurrency via `updated_at`/etag, and keep conflict UI client-side (no server decryption).
* Risks: Users can overwrite each other; but any semantic merge requires client-side diff tooling.
* Decision owner: Product + Architect.

### 5.6 Cycle check enforcement specifics

* Status: **NOT SPECIFIED IN DOCS** beyond “application layer + audit job”. 
* Recommendation: Implement immediate prevention in write path (reject relationship edge that creates cycle) + nightly audit job that logs ops_security_event_type `suspicious_activity` if cycles found (without storing node names).
* Risks: Poor cycle logic could block valid edits.
* Decision owner: Architect.
