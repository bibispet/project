## 0. Preamble

Project LORE is not “a family app.” It is a **sovereign family vault**: the “Safe Baby Book” today, and the “Sovereign Wallet” tomorrow. 
It is built so that families—not platforms—control the canonical record of identity and heritage. 

### 0.1 Immutable Business Requirements **LOCKED**

LORE is a **sovereign, zero‑knowledge family vault** that preserves family history for decades and protects identity from surveillance. 

**Non‑negotiables (binding invariants):**

1. **Kiosk Mode (“Grandma‑Simple”)**: a single prominent **“+”** capture button; **≤ 3 taps** to add a memory. 
2. **Zero‑Knowledge by construction**: user content is encrypted **before leaving the device**; servers store **ciphertext only**. 
3. **Verified vs Oral/Chosen**: **solid vs dotted connectors** must exist **end-to-end** (DB → API → Renderer). 
4. **18‑Year Lock / Transfer Ownership**: transfer protocol is **time‑locked until majority**. 
5. **No social feed mechanics**: **no likes/followers/viral loops**; this is a **vault/timeline** product. 

### 0.2 Terminology

**Account**: login identity (email / passkey). 
**Profile**: a person-node in the family graph (can be ghost/unclaimed). 
**Membership**: account ↔ family association. 
**Claim**: account ↔ “my profile node” binding. 
**Memory**: an encrypted media/story artifact attached to a **zone** and **focus profile** (timeline topology), with blobs stored as ciphertext in object storage. 

**UX Physics vocabulary (used throughout this document):**

* **Focus Node**: the currently-centered profile bubble; the anchor point for travel.
* **Generation Label**: the “G” bubble sitting above/between generations during travel states.
* **Parents**: two visual slots above the label (Left Slot A, Right Slot B).
* **Conveyor**: the memory stream moving along a fixed spine (never browser scroll).

## 1. System Architecture

### 1.1 Core Principle: Thick Client, Dumb Server **LOCKED**

Client performs: **encryption/decryption, timeline ordering, rendering physics, blind-index generation, key management**. 
Server performs: **auth/session, authorization gates, rate limits, metadata persistence, ciphertext blob routing**. 

**Hard prohibition:** Server **MUST NOT** contain decryption routines for user vault content. 

### 1.2 Components (Production Contract)

#### A) Frontend (Web‑first, physics‑locked)

* Stack target: React + TypeScript (Next.js acceptable). 
* Renderer: **custom DOM rail + SVG connector layer**. **No infinite-canvas graph libraries.** 
* Physics engine: deterministic motion/spring layer with a **hard FSM** (finite state machine). 

#### B) Backend (“Guard”)

* Stateless API + DB. 
* Issues presigned upload/download URLs for ciphertext blobs (object storage). 
* Enforces membership-based access gates to ciphertext. 

#### C) Database (Vault Index)

* PostgreSQL (dockerized, self-host). 
* Relationships stored as adjacency edges; recursive CTE for lineage traversal. 

#### D) Blob Storage (Ciphertext Object Store)

* Default: S3-compatible self-host (MinIO) or filesystem adapter. 
* Stores only encrypted bytes + minimal operational metadata. 

### 1.3 Reference Data Flows (Non‑Optional)

#### Flow: Create Memory (Upload)

1. Client collects file bytes, immediately stages them in memory (or streaming chunk buffer).
2. Client derives/selects DEK, encrypts **raw bytes + metadata blob** before any upload. 
3. Client requests presigned upload URL from Guard (plaintext operational metadata only: mime type, ciphertext size).
4. Client uploads ciphertext bytes to blob store via presigned URL.
5. Client creates/updates DB rows:

   * `memories` row with `encrypted_metadata_blob`, `privacy_level`, `timeline_sort_key`, zone fields. 
   * `memory_blobs` row with `ciphertext_sha256`, `ciphertext_size`, `mime_type`, `object_key`. 
   * `key_envelopes` rows for DEK distribution by privacy. 

#### Flow: Fetch Memory (Read)

1. Guard authorizes request (membership + privacy envelope existence).
2. Guard returns presigned download URL (ciphertext).
3. Client downloads ciphertext, decrypts locally, renders.

#### Flow: Search (Zero‑Knowledge)

* Client normalizes term → HMAC tokens; server matches tokens without seeing plaintext.

## 2. Data Classification — What is Plaintext vs Ciphertext

### 2.1 Ciphertext **LOCKED** (must never be plaintext server-side)

The following **must be encrypted on client** and must not exist as plaintext on the server:

* Profile “human meaning” fields (name, DOB, bio, photos, notes). 
* Memory payloads (media bytes, transcripts, story text). 
* Per-item metadata (title, description, location, tags). 
* Key material (ring keys, item keys, private keys). 

### 2.2 Plaintext (allowed operational metadata) **LOCKED**

Plaintext is allowed **only** if required for:

* relational integrity
* paging/querying
* access gating (who may fetch ciphertext)
* UI topology needs 

Examples explicitly allowed:

* UUIDs, family scoping IDs
* relationship edge endpoints (`parent_id`, `child_id`)
* relationship rendering flags (solid vs dotted)
* zone + ordering token (opaque)
* mime type + ciphertext size 

**Sovereignty rule (binding):** If the server can avoid knowing it, it must be ciphertext. 

### 2.3 Classification Ledger (Practical “Sovereignty Check”)

This section is a **design test**: if an engineer proposes adding plaintext fields, they must pass this ledger.

**Plaintext allowed**

* `relationships.relationship_kind`, `relationships.evidence_state`, `relationships.slot_hint`
  Reason: required for deterministic render topology (solid/dotted, left/right). 
* `memories.zone_anchor`, `memories.zone_focus_profile_id`, `memories.timeline_sort_key`, `memories.privacy_level`
  Reason: server must page/sort without decrypting. 
* `memory_blobs.mime_type`, `ciphertext_size`, `ciphertext_sha256`
  Reason: streaming & integrity of ciphertext. 
* `custody.eligible_at`
  Reason: server-enforced time lock gate (but DOB remains encrypted). 

**Ciphertext required**

* `profiles.encrypted_profile_blob`
* `memories.encrypted_metadata_blob`
* all wrapped keys / envelopes
* all media bytes
  Reason: Zero‑Knowledge invariants.

## 3. UX: Universal Drag Physics Engine **LOCKED**

This is the heart of LORE: the interface must feel like **physical tokens on a surface** (not “a webpage that scrolls”), while remaining logically deterministic and testable.

### 3.1 Absolute Rule: No Native Scroll Physics **LOCKED**

**BANNED in production UI:**

* wheel/trackpad inertia scrolling controlling timeline traversal 
* browser native scrolling as the source of truth for position 

**Required implementation posture:**

* main interaction surface uses `touch-action: none` 
* uses Pointer Events + pointer capture 
* all movement computed 1:1 from pointer deltas 

Accessibility: we may provide a setting that maps wheel events → synthetic drag deltas (still 1:1, no inertia). Default OFF. 

### 3.2 Topology (Restricted DAG) **LOCKED**

* **Time axis:** vertical (Y). 
* **Lineage axis:** horizontal (X). 
* **Render window:** max **2 generations** (Focus + Parents). 
* Above Focus: Y-split into Left (Slot A) and Right (Slot B). 

**Engineering interpretation (binding):**
Even if deeper lineage exists in DB, the renderer must never show more than Focus + Parents at once. Deeper navigation happens by travel sequences, not by drawing more nodes.

### 3.3 Deterministic Placement Rules **LOCKED**

* Standard: biological mother → left, biological father → right. 
* Same-sex / ambiguous: older partner → left, younger → right (deterministic). 
* Override: Edit-mode “Swap Left/Right” writes a persistent layout override. 

**v9.0 Clarification (Production Binding):**
“Layout override” is implemented by persisting `relationships.slot_hint = left|right` per edge (no separate override table required). 

### 3.4 Connector Styles **LOCKED**

We must render:

* **Solid:** verified biological 
* **Dotted:** oral/spiritual/chosen/step/unverified 

**v9.0 Rendering Truth Table (unambiguous):**

* Render **SOLID** iff:

  * `relationship_kind == biological` AND
  * `evidence_state == verified`
* Render **DOTTED** otherwise (including `chosen`, `oral`, `unverified`).

This rule exactly matches the product promise that “verified facts” are distinct from oral/spiritual bonds. 

### 3.5 Lens Toggle Behavior (Bio ↔ Chosen) **LOCKED animation sequence**

When toggling lens:

1. retract existing connector line back into generation label
2. fade out old node
3. draw new connector (solid or dotted)
4. fade in new node only **after** line reaches target 

**Tactile interpretation (the “unplug / re‑plug”):** the UI must *physically demonstrate* that the nature of the bond changed, not merely that content swapped.

### 3.6 FSM: Navigation Sequences **LOCKED**

FSM states and names are **binding**. 
Each state below includes:

* **Definition (Logic):** what must be true, what deltas apply, what clamps exist
* **Description (Feel):** what the user perceives (the “tactile story”)

## Sequence A: Travel to Past (Vertical Drag DOWN)

### STATE 0: REST

**Definition (Logic):**

* Focus anchored at lower-third.
* Gen label centered.
* Parents at upper-third. 

**Description (Feel):**

* The system is “assembled”: a clean Y-structure with two parent tokens resting above, ready to be entered.

### STATE 1: IGNITION

**Definition (Logic):**

* Trigger: pointer drag begins (DOWN).
* Focus subtly pins lower (begins transition into pinned mode). 

**Description (Feel):**

* The UI performs a fast **“implosion”**: auxiliary buttons collapse into the Focus node like it’s packing its bags for travel. 
* This implosion is deliberately *faster* than the main travel movement to communicate readiness (no clutter while moving).

### STATE 2: CONVEYOR

**Definition (Logic):**

* Focus is pinned.
* Memory nodes flow along fixed spine.
* Memories fade out before pinned Focus Y. 

**Description (Feel):**

* The screen becomes a **conveyor belt**: memories approach along the spine, slide past the user’s “hand,” then gently vanish just before colliding with the pinned token. 
* There is no scroll inertia; the user feels like they are pulling time itself, 1:1.

### STATE 3: ARRIVAL

**Definition (Logic):**

* User continues drag.
* Label + parents are pulled down 1:1 with pointer deltas. 

**Description (Feel):**

* The conveyor stops being a belt and becomes a tether: the user is now dragging the next generation down onto the stage.

### STATE 4: MERGE

**Definition (Logic):**

* Pinned focus merges into label.
* Label becomes new anchor for horizontal choice. 

**Description (Feel):**

* The Focus node “hands off” its identity into the Generation Label—like a token snapping into a socket—clearing the stage for left/right choice. 

---

## Sequence A2: Choose Parent (Horizontal “Rail”)

**Definition (Logic):**

* Global horizontal drag maps to movement along the bezier rail.
* Opposing branch fades linearly.
* Threshold rule is binding:

  * low velocity → must reach 100% overlap
  * release at <90% → snap back
  * high velocity flick → completes automatically 

**Description (Feel):**

* The user is not “panning a camera.” They are **pulling a parent bubble down the branch** and planting it into the center. 
* The opposing parent fades as the chosen one gains dominance, like two possibilities collapsing into a single committed path. 

**The “Grandma Drag” vs “Gen‑Z Flick” (tactile contract):**

* Slow, deliberate motion must require full placement (100%)—no surprise auto-complete. 
* Fast flick throws the token into place (velocity thresholded completion). 

**Completion event:**

* On lock completion: fire a distinct haptic **“clunk.”** 
* The subsequent growth animation draws stem and reveals parents only after lines reach their coordinates. 

---

## Sequence B: Travel to Future (Vertical Drag UP)

### STATE 1: CLEARANCE

**Definition (Logic):**

* Label + grandparents pulled off-screen 1:1. 

**Description (Feel):**

* The interface clears the stage; the same “implosion” happens at the start—buttons collapse inward to remove clutter. 
* Movement is pixel-locked (no autonomous scroll), creating direct manipulation confidence. 

### STATE 2: CONVEYOR

**Definition (Logic):**

* Vertical rail extends down.
* Focus pins top-center. 

**Description (Feel):**

* The rail becomes a hanging track beneath the pinned parent token. Memories rise upward along it, fading before impact. 
* On pin completion, fire the “clunk” (pin lock). 

### STATE 3: MORPH

**Definition (Logic):**

* Focus slides to top-left while label slides to center (simultaneous). 

**Description (Feel):**

* Two anchors move at once; the straight tension cable relaxes into a curved branch (a controlled morph, not user-driven). 

### STATE 4: CONSTRUCTION

**Definition (Logic):**

* Spouse fades in.
* Line draws.
* Stem draws down.
* Child fades in (“birthed”). 

**Description (Feel):**

* The next generation is assembled like circuitry:

  * spouse appears as a counterpart
  * connectors are drawn first
  * only when the stem reaches the landing point does the child appear—**not sliding**, but **manifesting** into place.

### 3.8 Haptics **LOCKED**

* Web: Vibration API if available; else audio/tactile fallback. 
* “Clunk” fired only on:

  * rail lock completion
  * conveyor pin completion 

### 3.9 Pointer Safety & Error States (v9.0 Clarification)

To preserve determinism across devices:

* Pointer capture must be acquired on drag start and released on completion/cancel.
* On `pointercancel`:

  * immediately transition to a safe snapback animation for the current sequence
  * return to STATE 0: REST
* Multitouch: only the first pointer is authoritative; additional pointers are ignored until release.

### 4.4 Sibling Drawer **LOCKED**

Adjacent to Focus node: Siblings button opens horizontal drawer. 
Drawer content obeys Bio/Chosen lens:

* Bio = biological siblings only
* Chosen = includes step/half/adopted where defined 

**v9.0 Clarification (unambiguous):**

* **Bio lens sibling computation:** siblings share **≥1 biological parent edge** with Focus.
* **Chosen lens sibling computation:** bio siblings + siblings connected via chosen edges (step/adoptive/guardian-like semantics), as represented by `relationship_kind=chosen`.

### 4.5 Visual System (Tactile “Laboratory” Feel)

The aesthetic should feel like **physical tokens resting on a surface**—scientific but warm. 

* Background: off-white with subtle dot grid. 
* Lighting: consistent soft shadows from top-left. 

**Node feel contract:**

* Nodes must have a slight “raised” affordance and a press/depress interaction to mimic tactile buttons.
* The “implosion” should feel like objects collapsing into the Focus bubble (packing/clustering), not fading away.

### 4.6 Empty Slots & Complex Families (v9.0 Gap Closure)

The topology is constrained to two parent slots visually, but real families can exceed two parent-like relationships.

**Binding rule:** the renderer never shows more than two parents at a time (Left Slot A / Right Slot B). 

**Overflow strategy (production requirement):**

* If >2 parent relationships exist in the active lens:

  1. Select the two that render by priority:

     * explicit `slot_hint=left/right` wins
     * else deterministic selection using (a) verified over oral/unverified, then (b) earliest `created_at`
  2. The remaining parents appear in an **“Other Parents”** list inside the Focus node’s expanded card (Read mode) and are editable in Edit mode.

**Empty slot behavior:**

* Read mode: empty parent slot renders as blank space (no placeholder).
* Edit mode: empty parent slot renders a subtle **“+ Add Parent”** affordance anchored to that slot (but only for the Focus node, consistent with “only attachable from current Focus node”).

4. Complete Better Auth account creation.

**Hard security invariant:** raw password and derived keys never appear in network payloads.

2. **Retention:**
   - `ops_security_events`: 90 days
   - `ops_job_runs`: 90 days
   - `ops_account_activity`: Lifetime of account
   - `ops_geo_fence_rules`: Lifetime of configuration (until explicitly deleted)

3. **Zero-Knowledge:** These tables MUST NOT store profile names, emails, raw IPs, request payloads, URLs containing IDs, or vault content (including any decrypted memory/profile metadata).

## 8. Security: Zero‑Knowledge Cryptography (Production Spec)

### 8.1 Crypto Primitives **LOCKED**

* Symmetric encryption: AES‑256‑GCM (Web Crypto)
* Key derivation: Argon2id preferred or PBKDF2 fallback
* Key wrapping/sharing:

  * preferred: X25519 sealed box (libsodium.js) for envelopes
  * fallback: ECDH + HKDF + AES‑GCM 

### 8.2 Key Hierarchy **LOCKED**

* **ARK**: derived from password/passkey secret + salt (client-only)
* **AKMK**: random 32 bytes; stored server-side only as Encrypt(ARK, AKMK)
* **Family ring keys**

  * `K_family` shared with family members
  * `K_inner` shared with inner circle via envelopes
* **DEK per memory** encrypts blob bytes + metadata; wrapped into envelopes by privacy_level 

### 8.3 Revocation Semantics **LOCKED**

Revoking access prevents future decryption via envelope removal; it cannot erase what someone already copied while they had access. 

### 8.4 Zero‑Knowledge Search (Blind Indexing) **LOCKED**

Client computes:

* normalize(term) → tokens
* token = HMAC(K_search, normalized_term)
  Server matches tokens without seeing plaintext.

## 9. The 18‑Year Protocol (Transfer Ownership) — Production Enforcement

This exists because the 18‑Year Lock is a business requirement. 
Pitch requires: dormant until majority, then key rotation + custodian keys burned. 

### 9.1 Custody Model **LOCKED**

Introduce table `custody`:

* `child_profile_id uuid pk fk profiles(id)`
* `custodian_profile_id uuid fk profiles(id)`
* `eligible_at timestamptz not null` (server-enforced time lock)
* `status custody_status_enum not null` (active | transferred | revoked)
* `created_at timestamptz` 

How `eligible_at` is set: client computes from DOB (encrypted) at creation time; stored plaintext as operational gate. This is a product time lock, not a court-grade age oracle. 

### 9.2 What “Burn Custodian Keys” Means **LOCKED**

Custodians have access only because they possess custody key envelopes.
“Burn” means remove/revoke custody-related envelopes that allow decryption beyond normal membership. 

### 9.3 Transfer Execution (Client-side, Zero‑Knowledge) **LOCKED**

When now ≥ eligible_at:

* Child claims their profile.
* Client generates new key material (new AKMK_child, new keypair).
* Client rotates keys / rewraps DEKs as allowed.
* Client requests server to mark custody transferred, revoke custodian envelopes, revoke custodian sessions/devices. 

### 9.4 Post-transfer Invariants **LOCKED**

* Custodian cannot regain privileged access unless the now-adult child explicitly shares keys.
* Transfer is irreversible at the envelope layer (no server-held master key exists).
